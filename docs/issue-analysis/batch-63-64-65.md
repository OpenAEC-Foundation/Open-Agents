## Issue #63: Local-First Chat UI — Open WebUI as Reference, Not Foundation

**Title**: `feat: local-first chat UI — Open WebUI als referentie, niet als fundament`

**Priority**: should-have
**Effort**: M (1–3 days)
**Hetzner Relation**: indirect (GPU server interface strategy)
**Sprint**: Sprint 20 (Desktop + Web App) / Sprint 21 (oa-cli as Product) — Web UI Command Centre phase
**Status**: Open

### Analysis

**What is the problem?**

Open WebUI was evaluated as a chat interface for the GPU server. Investigation shows that Open WebUI has progressively shifted toward OpenAI/paid provider integrations. Nearly every feature assumes an external API as the default, creating vendor lock-in risk for users seeking 100% local operation.

This misaligns with OpenAEC's open-source and local-first philosophy.

**Opportunity for Open Agents**

Open Agents should build its own chat interface with these guarantees:
- **Provider-agnostic** — local-first as default, not external APIs
- **Native integration** — directly with the oa-cli agent tree
- **No paid provider assumption** — optional, not mandatory
- **UX lessons from Open WebUI** — what works (model selector, conversation history, multi-user roles, markdown rendering, file upload) can be referenced but not copied

**Technical Direction**

The question: Should a local chat UI integrate into the existing oa-cli web interface (already running on `:1900`), or should it be a separate lightweight service on the GPU server?

**Proposed Solution** (100 words max)

1. **Scope**: Design a minimal chat UI component that wraps `oa-cli` agent execution
2. **Architecture**: REST endpoint `/api/chat` that pipes agent messages via SSE streaming (already implemented in MASTERPLAN)
3. **UX Reference**: Adopt Open WebUI's conversation history, model selector, and markdown rendering; skip multi-user roles (agents handle auth)
4. **Location**: Integrate into Sprint 21 Web UI Command Centre (Phases F1/F2/F3), not a separate service
5. **MVP**: Single conversation thread, agent selector dropdown, markdown responses, no file uploads yet

### Blocks

- Chat interface design and prototyping within Sprint 21

### Blocked By

- Sprint 21 Web UI foundation (currently 60% complete)
- `/api/assistant/chat` SSE streaming endpoint (✅ already implemented, see MASTERPLAN L-929, L-944)

## Issue #64: Remote Agent Spawn Fails on Root — `--dangerously-skip-permissions` Blocked

**Title**: `bug(remote): spawn_remote_agent fails on root — dangerously-skip-permissions blocked`

**Priority**: critical
**Effort**: S (< 1 day)
**Hetzner Relation**: direct-blocker (Hetzner dedicated server runs Claude Code as root)
**Sprint**: Sprint 22b (Remote Execution — LOW PRIORITY, but this is a blocker)
**Status**: Open

### Analysis

**What is the problem?**

Remote agent spawning via `oa run --remote hetzner` fails immediately on the Hetzner GPU server:

```
--dangerously-skip-permissions cannot be used with root/sudo privileges for security reasons
```

**Root Cause**

`spawn_remote_agent()` in `oa-cli/src/open_agents/spawner.py` (lines 75–93) builds the Claude Code command with `--dangerously-skip-permissions` (same as local agents). Claude Code v1.x explicitly blocks this flag when running as the `root` user for security reasons.

The remote server (root@144.76.60.210) cannot spawn agents at all.

**Technical Impact**

Remote machine spawning is completely broken for any server where Claude Code runs as root (common on VPS/dedicated hardware without non-root user setup).

**Proposed Solution** (100 words max)

**Option A (Recommended)**: Create non-root user (`agents`) on the Hetzner server. Update `remotes.json` to specify `remote_user: agents`. SSH key-based auth for passwordless spawning.

**Option B**: Replace `--dangerously-skip-permissions` with `--allowedTools` in the remote spawner. Build an allowlist of safe tools (bash, file I/O) instead of blanket permission skip.

**Option C**: Add conditional logic: detect remote user via SSH; if root, use Option B; else use current behavior.

**Recommendation**: Option A + create deployment docs (Option C as fallback).

### Blocks

- All remote agent execution on Hetzner
- Sprint 22b Remote Execution feature validation
- Chaining local ↔ remote agents in pipelines

### Blocked By

- None (can be fixed independently)

## Issue #65: Hook False Positive — `check-delegation.sh` Counts `&&` in Prompt Strings

**Title**: `bug(hooks): check-delegation.sh false positive — && in agent prompt counted as bash steps`

**Priority**: should-have
**Effort**: S (< 1 day)
**Hetzner Relation**: indirect (affects remote execution reliability if fix is not applied)
**Sprint**: Sprint 22 (Self-Improvement Foundation) — quality hooks
**Status**: Open

### Analysis

**What is the problem?**

The `check-delegation.sh` hook counts all `&&` occurrences in the full bash command, including those embedded in string arguments. This causes false positives:

```bash
oa run 'step 1 && step 2 && step 3 && step 4' --name my-agent --model claude/sonnet --direct
```

Even though `oa run` **is** the delegation mechanism, the hook treats the `&&` characters inside the prompt string as shell steps and blocks the command as "too many bash steps."

**Root Cause**

The hook analyzes the entire command line without distinguishing between:
- **Outer shell syntax** (the actual bash being executed)
- **Inner string content** (arguments to `oa run`)

**Current Workaround**

```bash
touch /tmp/claude-delegation-override && oa run ...
```

This is poor UX and masks the real issue.

**Proposed Solution** (100 words max)

**Fix 1 (Simplest)**: If command starts with `oa run`, exit 0 immediately. No further analysis needed — `oa run` **is** the delegation.

**Fix 2 (Precise)**: Only parse the "outer" bash command (everything before the first quote character). Ignore string arguments entirely.

**Recommendation**: Fix 1 — it's fast, safe, and correct. `oa run` is the boundary; anything inside its arguments is not shell syntax.

**Code location**: `~/.claude/hooks/check-delegation.sh` (or equivalent in oa-cli repo)

### Blocks

- Clean agent spawning without workarounds
- Documentation examples that use complex prompts with multiple steps

### Blocked By

- None (can be fixed independently)
